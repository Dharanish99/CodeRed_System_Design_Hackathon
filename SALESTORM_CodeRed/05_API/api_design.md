# API design
OpenAPI3.1 in openapi.yaml is the machine-readable source. Base URL is an example, not deployed. Bearer customer auth plus ownership on every resource; provider webhook uses verified signature. Commands never accept customer_id or payable amount from the client. Cart PUT has expected_version; reserve quantity must be1. Quote derives canonical price and eligibility from Catalogue/Sale; token is signed and bound to customer/product/sale/currency.
Idempotency-Key required for reserve, checkout, payment and cancellation. Scope=(principal,operation,key). Persist hash and original response; same body returns same original status/resource, changed body409. GET resource supplies current state rather than mutating stored original response. Business uniqueness additionally protects reservation/payment/order across different keys. Payment request hash excludes transient transport metadata but includes checkout and payment method identity; changing method requires terminal failure and a new reservation in this baseline.
201=durably created hold/checkout;202=payment/cancellation accepted pending resolution;400=input;401/403=auth;404=absent/not visible;409=OUT_OF_STOCK, EXPIRED, INVALID_STATE or IDEMPOTENCY_MISMATCH;429=admission;503=dependency unavailable/unknown commit. Retry-After and correlation_id included. No generic automatic retry of decline/409. After uncertain response use same key; NEVER infer a new charge is safe from HTTP timeout.
Checkout persists intent before Payment contacts provider. CheckoutStarted can cause the Payment worker to ensure an uncharged intent exists; a customer-supplied method attaches only to this same durable intent. Reconciler finds pinned checkouts with no Payment record and repairs creation. It cannot charge without authorized method. Unstarted pending intent can be terminally cancelled at provider before release; late messages cannot reopen it.
Payment response may be202 even if webhook resolves immediately; GET yields current outcome. Order absent while Checkout=SOLD means paid/order processing, not lost purchase. Webhook ACK only after durable receipt; invalid signatures401, unknown/conflicting references quarantined. Internal Inventory payment-application commands are broker events, not public HTTP endpoints.

For jury terminology, definitive provider success establishes business `CONFIRMED`; Inventory's event application then atomically records durable `SOLD` with the counter mutation, audit and `ReservationCommitted` outbox event. Public reads expose the durable status and payment outcome; they do not expose an artificial intermediate Inventory `CONFIRMED` status. `UNKNOWN` remains `PAYMENT_PENDING` and must be reconciled against the original provider intent.

Example: POST /reservations with Idempotency-Key buy-user42-sale7 and body {"inventory_id":"00000000-0000-0000-0000-000000000001","quantity":1,"quote_token":"signed-token"} ->201 Reservation. A retry returns the same reservation. Its current lifecycle is read via GET. Token and IDs here are illustrative only.
