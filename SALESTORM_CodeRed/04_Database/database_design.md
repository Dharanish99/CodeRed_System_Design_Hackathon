# Database design
See schema.sql for PostgreSQL DDL and erd.dbml/erd.mmd for matching logical relationships. Domain schemas represent separate ownership databases; co-location in this reference DDL aids review, not cross-owner writes.
Inventory stores allocated/available/reserved/sold, version and timestamps. Reservation stores customer reference, immutable quote, quantity, lifecycle, expiration, checkout ID and request identity. Payment stores one intent per reservation, stable provider key/reference and outcome. Order/OrderItem copy immutable paid line snapshots; reads never depend on live catalogue prices. Customer/product IDs in other domains are logical references validated at API boundaries; no distributed FKs.

The jury's business lifecycle includes `CONFIRMED → SOLD`. `CONFIRMED` is established by definitive payment success; it is represented in this schema by the payment outcome and audit evidence, then the same Inventory local transaction persists Reservation `SOLD`, counter changes and `ReservationCommitted`. It is intentionally not a separately durable reservation status, so no reader can observe a confirmed payment without the authoritative durable stock accounting.
Prices use bigint minor units and 3-letter currency; timestamps use timestamptz/UTC. IDs are UUIDs supplied by trusted service. Raw card data never enters these tables. Audit records actor, correlation, old/new status and reason; append-only role and immutable archival are operational requirements. SQL constraints plus service transition policy enforce allowed lifecycle; status CHECK alone does not enforce transition edges.
Cart multi-line storage is required by brief, but flash-sale checkout selects one line (A02). Coupons are uncapped percentage rules in this baseline; scarce global redemption limits would need an additional authoritative quota transaction, not a cache counter. Carrier callbacks require event dedup and monotonic state policy.
